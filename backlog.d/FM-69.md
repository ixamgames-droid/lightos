Titel: Bibliotheks-Update erreicht bestehende DBs nicht (SH-LASER3W ohne laser_x/laser_y)

**Herkunft:** Nebenfund DEMO-07 (Showcase-Shows, 2026-10-08): der Show-Lint meldete gegen eine gewachsene `fixtures.db` zweimal `EFX-ACHSE-FEHLT` fuer SH-LASER3W, gegen eine frische Bibliothek nichts. **Befund: die Vermutung im Titel stimmt nicht.** Die Profildatei `fixtures/bibliothek/shehds/3000mw-rgb-laser.json` traegt `laser_x`/`laser_y` seit ihrem ersten Commit (FM-61, #924). Eine nachgebaute alte DB (Achsen per SQL auf `pan`/`tilt`, Stempel der Datei veraltet) zieht `ensure_builtins` beim naechsten Start richtig nach, mit derselben Profil-ID (`_abgleichen` vergleicht ueber `_vergleichsform` auch die Kanal-Attribute). **Ursache:** die Demo-Shows werden in einer Wegwerf-Bibliothek gebaut und tragen deren Profil-Nummern. In einer gewachsenen Bibliothek zeigt die Nummer auf ein anderes Profil. `load_show` loest das ueber Hersteller und Modell auf (FM-43/FM-44), die DB-Pruefungen des Lints (`efx_achsen_check`, `dimmer_check`) nahmen aber die rohe Nummer. Dasselbe erklaert den ZQ02001-Befund aus DEMO-8. **Fix:** `dimmer_check.geraet_aus_patch` loest die Profil-Nummer ueber `show_file._resolve_fixture_profile_id` auf, wie das Laden. Die Meldungen fuer `load_show` werden danach zurueckgestellt. Alle drei DB-Pruefungen des Lints nutzen diesen Weg. Der Start der App ist nicht betroffen. Test `tests/test_fm69_bibliotheks_update_bestehende_db.py` (8 Tests, ohne den Fix 2 rot).
